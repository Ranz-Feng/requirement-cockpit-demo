# 写作规范与禁区

这份文档是交给架构师、算法和后端继续细化的产品输入，不是研发方案。只写“要什么”，把“怎么做”留给研发。

## 一、固定结构

只允许下面这些章节，顺序和名称固定：

```text
# <需求主题> 需求拆解
# 前言
# 版本信息
# 变更日志
# 需求背景
# 需求范围
## 【功能入口】
## 【新增功能】
# 需求拆解
## 【算法】
### 【算法功能】
## 【后端】
### 【后端需求】
```

不得新增效果定义、测试验收、风险分析、待确认清单、证据附录、研发建议等独立章节。效果、测试和风险内容分别写进算法功能、特殊情况处理等既有小节。

## 二、只补充什么

| 固定位置 | 只补充 |
|---|---|
| 前言 | 原始需求文档链接、密码、三份材料是否提供、是否经过最新评审 |
| 版本信息 | 版本号、创建日期 |
| 变更日志 | 时间、版本号、变更人、主要变更内容 |
| 需求背景 | 七个时间节点 |
| 功能入口 | 入口位置、进入方式、与现有功能的区别、入口截图情况 |
| 新增功能 | 建设内容、流程简要说明、特殊情况处理 |
| 算法功能 | 建设能力、效果与边界、流程与输入输出、算法实验 |
| 后端需求 | 后端建设内容、前端配合点、模型或算法能力、特殊情况 |

清单之外的内容不擅自增加。确实有必要但模版没有位置的，合并进最接近的固定小节；无法归入或不确认的，不写，也不要另开章节。

材料没给的信息不用写成待确认或待补充：模版里有字段的留空，没字段的就不写。

前言不复述材料内容，不写"业务口径以某材料为准"这类综述，也不堆"历史人工拆解：未提供"之类的元信息。版本号和日期沿用材料里的写法（如"客户端V13.4.0""2026年10月10日"），不套默认的 `1.0.0` 格式。

## 三、默认写法

- 段落、分点、编号、表格和流程图按内容形态选，不按个人习惯选。形态细节见 `05-表达形态与结构选择.md`。
- 一条主线的解释、背景、目标和总述写段落；三条以上同级、无先后的项分点；有先后或优先级的排编号；多对象同维度对比、固定取值集和指标口径做表格；端到端链路、分支和兜底用流程树或 Mermaid。
- 固定小节尽量落到对应形态：新增功能用路径对照表，算法功能用"项 / 取值与规则"表和"指标 / 口径"表，后端需求用"路径 / 前端负责 / 后端负责"表。确实没有可对比内容时才不用表。
- 单个要点超过 2 到 3 行还在往里塞并列信息，就拆成分点或表格。一句话里连续出现"并且、同时、另外、分别、包括"三处以上，多半该拆。
- 解释性内容合并成简洁段落，不要切成一堆一句话 bullet；可枚举的规则也不要全挤成一整段。
- 表格单元格只放短结论，细节留给段落。
- 材料有入口截图时保留截图说明；没有可随文档交付的图时，用一行文字描述截图内容（例如"现网入口-一键成片·视频模版选择页 / 点击顶部音乐栏"），不写指向本地相对路径的图片链接（如 `./assets/xxx.png`）。
- 先给结论，再给条件、边界和异常。
- 用可验收的表达。“效果好”“尽量准确”“注意性能”都不能作为结论。
- 指标必须可计算；材料没有给出依据的数值只写定性口径，不拍脑袋写数字。
- 术语沿用材料中的叫法，不另造字段、状态和接口体系。
- 不写套话、方法论和没有动作的“建议加强关注”。

## 四、产品与研发边界

产品侧可以写：

- 用户从哪里进入、看到什么、能做什么。
- 功能范围和边界。
- 成功、失败和降级的业务表现。
- 效果指标、口径、基线与目标。
- 算法实验目的、样本和通过标准。
- 后端需要建设的业务能力与结果去向。
- 前后端各承担什么功能责任。
- 特殊情况下的业务处理与默认方案。

产品侧不写：

- 字段名、字段类型、是否必填、默认值、枚举取值。
- JSON/XML 结构、接口报文、错误码、接口协议。
- 状态机英文枚举、服务拆分、表结构、索引、存储路径。
- 模型架构、调用方式、框架、中间件、代码逻辑；不自行指定模型。材料或历史拆解里已明确的模型名、厂商或能力来源可以照写，材料没给的不推荐、不编造，写"模型待确认"或"由算法与研发评估后确定"。
- 部署方案、容量规划、轮询间隔、长连接或回调机制。
- 排期承诺、人力投入和未经确认的上线日期。

模版里出现“输入输出字段”“调用什么模型”“错误码”时，只写产品需要的业务信息类别、能力要求与兜底表现，并明确提示“字段、选型和具体定义由研发补充”。

## 五、证据与假设

- 锚点用于内部核对，不是逐句装饰。同一小节、同一来源标一次即可，关键结论只使用 `[原型]` 或 `[评审会议录音]`；用户要干净的成稿版时，正文可以不标锚点，只在前言写清材料来源。
- 不标页码、时间戳、段落号、说话人或历史拆解位置。
- 历史人工拆解只用于参考结构和写法，不作为事实证据。
- 无来源推断标 `[推断]`，且不能进入目标效果、实验通过标准和风险等级。
- 没有依据的内容不写，也不留成待确认条目。
- 材料冲突时按更保守、更贴近用户的一次口径落笔，不写成待澄清问题。
- 算法实验里，对比基线、通过标准和复测方式是可选项：材料提到才写，没提到不自行补。

## 六、反模式

| 反模式 | 为什么不行 | 正确做法 |
|---|---|---|
| 新增“测试与验收”章节 | 超出固定模版 | 写进【算法功能】的“算法实验” |
| 新增“风险与待确认”章节 | 超出固定模版 | 写进“特殊情况处理”并给出处理方式 |
| 自定义 `task_id` / `status` / `error_code` | 替研发定义了协议 | 写业务信息类别和用户可见结果，定义留给研发 |
| 写模型架构和调用方式 | 实现细节越界 | 写需要什么模型能力、业务任务和质量约束 |
| 写接口请求和 JSON | 实现细节越界 | 写输入输出业务信息类别，结构留给研发 |
| 写存储路径和轮询间隔 | 实现机制越界 | 写结果在哪里对用户可见、何时可见 |
| 写本地相对路径图片链接 | 链接交付不了，读者看不到图 | 一行文字描述截图内容，或随文档交付真实图片 |
| 自行指定或推荐模型名 | 模型选型不是产品结论 | 材料已明确的照写，未明确的写"模型待确认" |
| 自行补实验基线、通过标准、复测方式 | 材料没给依据 | 材料提到才写，没提到就不写 |
| 把假数据当业务规则 | 来源不可靠 | 只作样式线索，规则缺失就不写 |
| 列一长串待确认、待补充的问题 | 评审会自然补齐，文档不承担这项职责 | 只写材料支撑得住的产品结论 |
| 大量一句话 bullet | 信息碎、关系不清 | 解释性内容合并为简洁段落 |
| 把并列规则挤进一整段 | 关系被埋住，研发要自己拆 | 拆成分点或表格 |
| 多对象对比写成流水句 | 有差异看不出来 | 做表格 |
| 该有先后的写成无序分点 | 看不出执行顺序 | 改成编号 |
| 链路和兜底只写文字 | 分支和回退看不清 | 补流程树或 Mermaid，文字留要点 |
| 大量 `###` 新标题 | 破坏固定模版 | 只用模版规定的两个 `###` |

## 七、脱敏

材料包含真实用户数据、密钥、联系方式时，示例值脱敏后再写入。脱敏保留逻辑关系，不附原值与替换值的映射表。
