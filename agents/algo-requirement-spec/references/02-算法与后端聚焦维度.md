# 算法与后端聚焦维度

只在下述固定章节里补充内容。材料没有给出依据时保留字段、值留空，不新增章节，不替研发定义实现，也不列待确认事项。每个小节用段落、分点、编号、表格还是流程树，按内容形态选，规则见 `05-表达形态与结构选择.md`；和人工成稿的对齐做法见 `06-与人工成稿对齐.md`。

## 一、前言

只留三件事：

- 原始需求文档链接、文件名或来源。
- 访问密码；没有写"无"。
- 需求原型、评审录音、历史人工拆解是否提供；缺评审录音时写明"未经最新评审确认"。

不复述材料内容，不写"业务口径以某材料为准"这类综述，不堆"历史人工拆解：未提供"之类的元信息。没有链接或密码时留空，不编造。

## 二、版本信息与变更日志

版本信息只写版本号和创建日期，沿用材料里的命名和日期写法，例如"客户端V13.4.0""2026年10月10日"，不套用默认的 `1.0.0`、`2026-10-11` 格式。变更日志表只写时间、版本号、变更人、主要变更内容；变更人按模版默认或材料中明确的作者填写，没有依据再留空，不把 AI 或模板里的示例姓名当成本次变更人。只写本次这一条。

## 三、需求背景

只写七个时间节点：最晚评审时间、开发时间、联调时间、端测时间、平台上线、合规测试、CTC验收。

- 优先从原始需求文档和评审录音里把这些节点提取出来填满。
- 材料只写"待定""后续同步"或没提到的，保留字段并留空，不从上线计划倒推。
- 每个节点都保留，不能因为不知道就删行。

## 四、需求范围

### 【功能入口】

要回答：新增功能入口在哪里，用户从哪里进入，和现有功能有什么区别。

- 写清页面、位置、入口名称和进入条件。
- 材料有入口截图时引用或保留截图说明，体现图文并茂；没有截图时用一行文字描述截图内容，例如"现网入口-一键成片·视频模版选择页 / 点击顶部音乐栏"。
- 不写指向本地相对路径的图片链接（例如 `./assets/xxx.png`），除非确认该资源会随文档一起交付。
- 多个入口或多条路径并列、需要对比时，用一张对照表；只有一个入口就用段落加截图说明。
- 只写用户可见差异，不写技术实现差异。

### 【新增功能】

只补三点：

1. **需要建设什么。** 先写一段总述讲清产品范围和主要能力，再按路径用编号逐条列出。多条路径共用同一结果时，用一张对照表把"模块 / 路径 / 用户可选的来源 / 能力与限制 / 列表与展示 / 结果去向"并排说清。
2. **流程简要说明。** 从用户触发写到结果可用或失败，说明同步、异步、等待和结果去向。有先后顺序时用编号或流程树，结尾用一句话点明哪些是即时返回、哪些是异步任务。
3. **特殊情况处理。** 逐条用分点写空结果、超时、重复提交、内容违规、上游不可用、部分成功等业务情况和兜底动作。

错误码、接口协议、存储位置和具体技术实现由研发补充。产品侧只写用户看到什么、业务上退到哪里。

## 五、【算法功能】

### 需要建设的算法功能

按能力逐条编号列出，提取、生成、润色等各占一条，每条写清能力本身与用途。本版明确不做的能力也单列一条，材料说明原因时把原因写上（例如厂商接口不支持素材分析），不写模型架构、算法公式、框架和代码。

合格标准：算法同学看完能判断要建设哪些能力、服务哪些业务场景、和现有能力是否重叠。

### 目标算法效果、示例、规则预设、能力边界与特殊情况

按下面的分工写：

| 项 | 产品要写什么 | 用什么形态 |
|---|---|---|
| 目标效果 | 做成后是什么表现，用户或业务能感知到什么 | 分点，每条一个目标 |
| 成功示例 | 用业务语义描述一个正确结果 | 分点 |
| 失败示例 | 用业务语义描述一个不可用结果 | 分点 |
| 规则预设 | 已确认的判断规则、优先级、固定取值集（形态、时长、格式、歌手性别等） | "项 / 取值与规则"表格 |
| 效果指标 | 指标口径、分子分母、统计窗口 | "指标 / 口径"表格，统计窗口单独一行 |
| 能力边界 | 能做什么、不做什么、边界外如何处理，有原因一并写 | 分点 |
| 特殊情况 | 空输入、超长、无结果、内容违规、模型异常、上游异常等 | 分点 |

指标必须可计算。材料没有给出依据的基线、目标值和阈值只写定性口径，不写具体数字。不写模型架构、算法公式和实现结构；材料或历史拆解已明确的模型/厂商名可以照写。

### 大致流程、输入输出字段

| 项 | 产品要写什么 | 不写什么 |
|---|---|---|
| 大致流程 | 端到端链路、分支和兜底，从用户触发写到结果回流，用流程树表达 | 服务拆分、调度机制、代码流程 |
| 输入内容 | 需要哪些业务输入、来源和前置条件，用分点列 | 字段名、字段类型、枚举、默认值 |
| 输出内容 | 用户或下游能看到哪些业务信息、粒度与用途 | 返回结构、错误码、JSON/XML |
| 返回时机 | 同步还是异步、用户何时能看到结果 | 轮询间隔、长连接、回调实现 |

把推荐、导入、生成各路径的分支以及失败或取消分支都画出来，文字只留要点。在流程树后用分点补充输入输出的业务类别、来源、形态与返回时机，并明确一句"字段名、类型和结构由研发补充"。

### 算法实验

这里同时承担测试要点和效果验收功能，不新增测试章节。用编号分出两类：

1. **正向样本。** 样本来源、覆盖场景用缩进分点写在下面，目的用一句话说清。
2. **负样本。** 同上，列出需要被正常拦截的输入类型。

对比基线、通过标准和复测方式为可选项：材料明确提到就写，没提到就不写，不自行补充。指标口径已经在目标效果处列过，这里不重复。材料没有给出依据的样本量和阈值只写定性要求，不写具体数字。不写训练参数、模型结构和工程实现。

## 六、【后端需求】

### 需要建设的后端功能

先用一句话总述处理范围与结果去向，再按能力用分点逐条列出，例如曲库升级、列表归集、导入与上传承接、生成任务、内容合规。范围到业务处理和结果去向为止，服务如何划分、数据如何组织由研发决定。

不写服务拆分、表结构、存储路径、消息队列、缓存、部署和代码逻辑。

### 需要和前端配合的地方

先用一句话说明结果去向，再用一张"路径 / 前端负责 / 后端负责"表格把各路径职责并排写清；表格后用一段收尾说明试听方式、空态、失败重试、任务进行中允许离开页面等共性表现。如果原型或材料点明了平台限制（例如 iOS 本地音乐的沙盒限制），在同一段里写清。

只写功能责任，不定义接口地址、请求方法、字段结构、错误码、状态枚举和轮询机制。

### 调用什么模型

按能力分点列出，每类写清业务任务与约束。材料或历史拆解已明确具体模型、厂商或能力来源时，照写名字；材料没给的一律写"模型待确认"或"由算法与研发评估后确定"，不得编造模型名，也不写模型架构与调用方式。质量与合规约束单独说明。

### 特殊情况处理

覆盖：异常、超时、空结果、内容违规、重复提交、降级、部分成功、上游不可用和成本超限。每项尽量写清：

- 触发条件。
- 业务上如何处理。
- 用户最终看到什么。
- 是否有默认处理方式。

不新增"风险"章节；风险在本节内随对应功能说明，并直接给出处理方式，不写成待确认条目。

## 七、通用质量判断

- 架构师能判断范围、依赖和边界。
- 算法能判断要建设的能力、效果定义和实验要求。
- 后端能判断业务处理范围、结果去向和前后端配合点。
- 测试能依据"算法实验"和"特殊情况处理"准备验证方向。
- 文档里每条结论都有材料支撑，没有留待澄清的空条目。
