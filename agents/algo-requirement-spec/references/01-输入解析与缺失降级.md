# 输入解析与缺失降级

三份材料的角色不同、可信度不同。混着读是这份文档最大的错误来源。

## 一、需求原型 PDF：界面与可见行为来源

原型回答“界面上有什么”，不回答“为什么”和“后端怎么做”。

| 类别 | 可提取内容 | 写法 |
|---|---|---|
| 功能入口 | 页面名称、入口位置、层级关系、与现有入口的区别 | 写进【功能入口】 |
| 用户操作 | 按钮、控件、必填校验、默认状态、二次确认 | 写进新增功能或流程说明 |
| 用户可见结果 | 展示内容、空态、加载态、失败态、文案 | 写进新增功能或后端配合事项 |
| 状态线索 | 原型上已经画出的用户可见阶段 | 只描述用户看到什么，不定义状态名与状态机 |
| 图片 | 入口截图、关键页面截图 | 有图则引用，没图则写“入口截图待补充” |

读原型的注意点：

1. 原型上的假数据不是真实取值域，只能当展示样式线索。
2. 原型没画不等于不需要，缺失部分不替它下结论，也不在文档里写成待确认事项。
3. 原型上的字段只作引用，产品不另造字段、类型和枚举。
4. 扫描件 OCR 的数字与专有名词要提示人工核对，锚点仍只写 `[原型]`。

## 二、需求评审录音：最新业务口径来源

录音回答“最后怎么定的”，但讨论过程不等于结论。先判断每段属于什么：

| 类型 | 识别特征 | 处理方式 |
|---|---|---|
| 明确结论 | “就按……做”“定下来”“这次先不做” | 可作为确定依据 |
| 待办承诺 | “回去看一下”“下周给答复” | 不当作结论使用，也不写进文档 |
| 讨论过程 | 多轮来回但没有收口 | 不写成结论 |
| 反驳与否定 | “这个不行”“不能这么做” | 写进能力边界、禁止项或特殊情况 |
| 未提及 | 材料里没有 | 不自行补全 |

正文锚点统一写 `[评审会议录音]`，不写时间戳、段落号或说话人。内部定位信息只留在原始材料里。

## 三、历史人工需求拆解：结构与写法来源

历史文档回答“以前是怎么拆的”，是参考，不是本次事实。

可以借：章节结构、拆解维度、术语习惯、模块称呼、责任边界写法、交付物粒度和表达口径。

不要借：上一版具体业务内容、具体数值、旧结论、旧排期与旧人员承诺。

历史文档不标证据锚点，也不直接复制到新文档。

## 四、缺失降级

材料可以不全。缺哪份就按下面降级，不用推测冒充来源。

| 缺什么 | 怎么继续 | 文档里怎么写 |
|---|---|---|
| 缺评审录音 | 照常产出，业务口径以原型和历史写法为限 | 前言写“未经最新评审确认”；受影响的内容只写材料能支撑的部分 |
| 缺历史拆解 | 不影响产出，按固定模版自行补齐维度 | 前言注明“未提供” |
| 缺原型 PDF | 只能参考历史结构和现有业务描述 | 功能入口和流程只写能确认的部分，其余留空 |
| 只给一份材料 | 只写可确认部分，其余保留固定小节 | 未覆盖的部分保留字段并留空 |
| 三份都缺或极薄 | 先问 1–3 个关键问题 | 未确认前只给固定章节框架，不填结论 |

没有录音时的固定动作：在前言写“未经最新评审确认”，照常产出；依赖评审口径的内容不作延伸，能被原型和历史写法支撑的部分照常写。

## 五、冲突处理

不把冲突整理成待澄清条目。按下面更保守的一条落笔，正文只写采用的口径。

| 冲突组合 | 处理 |
|---|---|
| 原型与录音 | 录音通常更新，按录音落笔 |
| 原型与历史拆解 | 优先原型，历史文档只作写法参考 |
| 录音与历史拆解 | 优先录音，历史文档视为过期口径 |
| 三者互斥 | 取更贴近用户、更保守的一次口径落笔，不列待澄清问题 |

## 六、事实卡

抽取阶段先登记事实，不直接下结论。每条事实至少写：

```text
事实ID：
类别：
事实内容：
来源：[原型] / [评审会议录音]
是否已收口：
未收口的点（仅内部参考，不写入文档）：
```

事实卡只作为内部整理，不进入最终文档。
