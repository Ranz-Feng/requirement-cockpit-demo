# 导入后可直接试用的用例

## 用例 1：三份材料齐全

> 这是需求原型 PDF、评审录音转写和历史需求拆解文档，请按固定模版出一版需求拆解文档，只补充模版规定的内容。

期望：产出与固定模版章节一致的文档；来源只用 `[原型]` 或 `[评审会议录音]`，不带页码、时间戳与段落号，同一小节同一来源标一次即可；指标口径可计算，材料没给依据的数值不写具体数字；不出现自定义字段名、JSON 结构、错误码与状态机枚举；不新增独立章节，也不列待确认清单。

## 用例 2：没有评审录音（重点验证降级）

> 这次只有需求原型 PDF 和历史拆解文档，评审录音暂时没有。请照常产出，并把因为缺录音而无法确认的口径标出来。

期望：不索要、不停工；在【前言】注明"未经最新评审确认"；依赖评审口径的内容不作延伸，也不列待确认清单。

## 用例 3：只有一句话

> 要给搜索结果加一个智能问答入口，具体细节还没定，先出一版框架。

期望：产出固定模版的章节框架，材料没给的位置留空；不虚构指标、样例或业务规则，也不列待确认事项。

## 用例 4：验证不写实现

> 帮我继续补充【算法功能】和【后端需求】，把架构和表结构一起写了吧。

期望：说明实现设计不在本专家范围内，改为补全产品层的能力边界、输出内容形态与业务约束、异常降级，并提示字段、接口与结构细节由研发在设计阶段确定。

## 用例 5：局部修改

> 把【算法功能】里的效果口径改成按自然月统计，其他不变。

期望：只改指定内容及其直接关联处，保留其余文字与结构；不重讲整个方案，也不新增章节。

## 用例 6：验证不替研发定细节

> 帮我把输出结构写细一点，给出字段名、状态枚举和出错时的错误码。

期望：说明字段、状态与错误码由研发定义，产品侧只补充要表达哪些业务信息、用户看到哪些阶段、失败时看到什么；行文按内容形态选，解释性内容写段落，并列规则分点，不做实现设计。

## 用例 7：验证行文形态

> 这条需求里有多条并列规则、一组参数取值和一个端到端链路，请写清楚一点。

期望：并列规则用分点，有先后的流程用编号，参数取值和多对象同维度对比用表格，端到端链路与兜底补流程树；不把上述内容挤成一整段，也不碎成一堆一句话 bullet，不新增章节或标题。

## 用例 8：对齐人工成稿的干净版

> 材料里提到了模型名和厂商，给一版可以对外交付的干净稿，不要标来源锚点，也不要用本地图片链接。

期望：前言只留链接与密码，版本号与日期沿用材料写法；正文可完全不标锚点；不写指向本地相对路径的图片链接，没有可交付图片时用一行文字描述截图；材料已明确的模型/厂商名照写，未确认的写"模型待确认"；新增功能有路径对照表，算法功能有规则与指标表，后端需求有前后端职责表；不自行补实验基线、通过标准和复测方式。
